## 1. 背景

平台有三种交付形态，对持久层的要求不同：

| 形态 | 场景 | 持久层诉求 |
|---|---|---|
| Electron 桌面端 | 单机离线安装 | 单文件、零运维、可随用户数据目录读写 |
| Docker 演示（答辩） | 单机一键启动 | 单文件、随容器卷挂载 |
| 服务端部署 | 多人并发 | 并发写、并发读、备份、迁移 |

上游参考项目 ZNCBZS 使用 SQLAlchemy 2.0 + PostgreSQL，RWP 使用 SQLite。

## 2. 候选选项

| 选项 | 说明 | 结论 |
|---|---|---|
| A. 全量 PostgreSQL | 单一形态 | ❌ 桌面端与离线演示场景需携带 DB 进程，破坏「免运维」目标 |
| B. 全量 SQLite | 单一形态 | ❌ 服务端并发写能力不足，审计日志与告警写入会争锁 |
| C. 双形态：SQLite（桌面/演示）+ PostgreSQL（服务端），SQLAlchemy 抽象 | 见下 | ✅ **采纳** |

## 3. 决策

**采用 C**，边界规则：

- **SQLite** 是默认形态（`api/db/database.py` 裸 `sqlite3`，文件 `platform.db`）：桌面端、演示、单机使用一律走 SQLite；
- **PostgreSQL** 是服务端形态的可选底座：需要多用户并发、长期留存审计与预警流水时启用；
- **访问层必须保持方言中立**：SQL 构造不得使用 SQLite 专有语法（如 `INSERT OR REPLACE`、`strftime`）或 PostgreSQL 专有语法，日期格式化统一走 Python 侧；
- **迁移路径**：优先用 SQLAlchemy 2.0 `Mapped` 风格重写 `api/db/database.py`，把裸 `sqlite3` 收敛到 Repository 层，为双后端留出切换点（当前为裸 sqlite3，是本 ADR 未完全落地的部分）。

## 4. 后果

**正面**：桌面端交付体验不打折；服务端形态有升级路径。

**负面**：目前访问层直连 `sqlite3`，切换 PostgreSQL 需要重写；迁移期需维护两套 DDL；`api/db/seed.py` 的内置数据播种需在两种后端下验证幂等。

**约束**：在访问层完成方言抽象之前，**不得**在服务端形态中直接替换 DSN——这属于「看起来支持、实际未验证」的伪支持。
