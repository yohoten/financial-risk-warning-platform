# 文档编写与状态治理规范

> | 元信息 | 值 |
> |---|---|
> | 状态 | ✅ 生效 |
> | 版本 | v1.0 |
> | 日期 | 2026-11-19 |
> | 适用范围 | `docs/` 目录下全部 Markdown 文档，以及根 `README.md` 的文档索引部分 |
> | 目的 | 解决「文档越来越多，但不知道哪份是当前口径」的历史问题 |

---

## 1. 为什么需要这份规范

2026-11-19 之前的文档体系存在三个结构性问题：

1. **索引不全**：`docs/design/` 16 篇中 6 篇未进索引，`docs/analysis/` 7 篇、`docs/literature/` 2 篇、`docs/Attachment/` 全部未进索引；
2. **状态不明**：《中期可行性分析与建议方案设计》（2026-11-13）的结论已被后续修复超越 4/5，但读者无从判断，容易误用；同一主题存在 3 份并存文档（`FastAPI服务层设计` / `前端架构与图表方案` / `平台功能与预测设计`）且内容互不引用；
3. **路径失效**：目录重组后链接未同步，12 处论文链接、9 处子目录文档链接失效。

根因不是「不写文档」，而是**没有文档生命周期约定**。本规范补上这一环。

## 2. 元信息块模板

**每篇文档开头必须有以下元信息块**（顺序固定）：

```markdown
> | 元信息 | 值 |
> |---|---|
> | 状态 | ✅ 已实现 / 📝 设计稿 / 📊 分析结论 / 🔄 被取代 / ⛔ 已废止 / 🟡 待决 |
> | 版本 | vX.Y |
> | 日期 | YYYY-MM-DD |
> | 取代关系 | 取代《…》/ 被《…》取代 / 无 |
> | 证据边界 | 本文档结论的依据范围与限制 |
> | 关联文档 | 《…》、《…》 |
```

### 2.1 字段说明

| 字段 | 必填 | 说明 |
|---|:---:|---|
| 状态 | ✅ | 见 §3 的状态语义表 |
| 版本 | ✅ | 主版本号随**不兼容变更**递增，次版本号随内容增补递增 |
| 日期 | ✅ | 最后一次实质性修改日期（纯格式修正可不变） |
| 取代关系 | ✅ | 明确本篇与其他文档的取代/被取代关系；无则写「无」 |
| 证据边界 | ✅ | 说明结论基于什么（代码？产物？文献？），以及**不覆盖什么** |
| 关联文档 | 选填 | 横向关联的文档（相对链接） |

## 3. 文档状态语义

| 标记 | 语义 | 判定标准 | 读者应如何对待 |
|---|---|---|---|
| ✅ **已实现** | 与当前代码事实一致 | 已上线且行为可验证 | **可直接依赖** |
| 📝 **设计稿** | 方案已定稿，实现已完成或待补验收记录 | 有明确目标架构与实施步骤 | 读作「意图」，具体行为以代码为准；验收记录补齐后转 ✅ |
| 📊 **分析结论** | 某一时点的诊断/评估结论 | 有明确观察时点 | **可能已被后续修复超越**，引用前须核对状态说明 |
| 🔄 **被取代** | 已被更新口径取代 | 存在明确的后继文档 | **仅作历史留存**，禁止引用其数据与结论 |
| ⛔ **已废止** | 结论或路径已失效 | 路径错误、结论被推翻 | **禁止引用**，保留仅为追溯 |
| 🟡 **待决** | 问题已识别、方案已给出 | 存在 ADR 但未实施 | 按 ADR 标注的阶段执行 |

### 3.1 状态转换规则

```
新建文档 ──► ✅ 已实现（默认）
   │
   ├── 方案已定但未落地 ──► 📝 设计稿
   │
   └── 一次性诊断报告 ──► 📊 分析结论
                              │
                              └── 结论被超越 ──► 🔄 被取代 ──► ⛔ 已废止（可选）
```

**禁止**：把 📊 分析结论直接改写为「已解决」而**不说明哪些结论仍成立**。正确做法是**保留原文 + 在顶部状态块中标注「4/5 已修复，待决项见 ADR-xxx/yyy」**。

> 范例：《中期可行性分析与建议方案设计》→ 状态标 `📊 分析结论（🔄 部分被取代：5 项修复中 4 项已落地，仅预处理泄漏待决，见 ADR-007 / ADR-010）`。

## 4. 文档分区与职责

| 目录 | 职责 | 生命周期 | 典型读者 |
|---|---|---|---|
| `docs/design/` | **研究与系统设计**：调研、方案、架构、ADR、契约 | 长期，随版本演进 | 开发者、评审、答辩评委 |
| `docs/analysis/` | **数据与可行性分析**：字段可用性、缺口清单、补齐进展 | 随数据更新刷新，保留历史版本 | 数据分析者、论文作者 |
| `docs/literature/` | **文献与资料**：检索策略、资源清单、精读笔记、PDF 原文 | 长期，PDF 只增不改 | 论文作者 |
| `docs/Attachment/` | **论文交付包**：论文正文稿、参考文献、Word 版、学校模板 | 与论文版本同步 | 导师、评审 |
| `docs/README.md` | **全量索引**：四分区入口 + 状态标记 | 每次文档变更都需更新 | 所有人 |
| `README.md` | **项目门面**：快速开始、功能特性、结构树、文档索引 | 每次功能变更都需更新 | 所有人 |

### 4.1 命名约定

| 规则 | 说明 |
|---|---|
| 中文名 | 保持项目既有风格（如 `系统架构设计说明书.md`） |
| 日期后缀 | 时点性文档用 `_YYYYMMDD`（如 `平台优化设计方案_用户权限与实时接入_20261117.md`），不带空格 |
| ADR | `adr/ADR-NNN-主题短句.md`，编号三位、递增、不复用 |
| 证据冻结 | 数字真源**唯一**文件：`证据冻结清单.md` |

## 5. 写作规范速查

沿用项目既有约定（`docs/README.md` §四）：

| 项 | 规范 |
|---|---|
| 参考文献格式 | 中文 GB/T 7714-2015；英文 APA 7th |
| 图表编号 | 图 X-Y / 表 X-Y；图注在下、表注在上 |
| 术语统一 | ST/*ST、财务困境（financial distress）、可解释性（XAI）、SHAP 值（log-odds 贡献） |
| 数字口径 | AUC / KS 保留 **4 位小数**；概率保留 **2 位**百分数；金额统一**亿元** |
| Mermaid | 置于代码块内，保持可渲染（GitHub / Typora / VS Code） |
| 编码 | UTF-8 无 BOM，LF 换行（仓库已配置 `core.autocrlf` 行为，提交前确认无 CRLF 混入） |
| 链接 | **相对链接**（`./xxx.md`），便于目录整体移动；不使用绝对本地路径 |
| 路径引用 | 代码路径用反引号并给出关键行号（如 `etl/clean_financial.py:60`） |
| 数字引用 | 必须能对应到《证据冻结清单》的条目编号 |

## 6. 新增文档流程

```
① 起草（套用 §2 元信息块 + §5 写作规范）
      ↓
② 自检（链接可达 / 数字有出处 / 状态标记正确）
      ↓
③ 登记到 docs/README.md 对应分区（表 + 状态标记 + 建议阅读顺序）
      ↓
④ 若涉及项目门面，同步根 README.md 的「文档索引」表与「功能特性」表
      ↓
⑤ 提交（建议消息格式：docs(<主题>)：<一句话说明>）
```

**检查清单**

- [ ] 元信息块六字段齐全
- [ ] 状态标记与实际一致（文档声称已实现 → 代码确实已实现）
- [ ] 所有相对链接可达
- [ ] 所有指标数字可对应到《证据冻结清单》
- [ ] 已登记到 `docs/README.md`
- [ ] 若改变了项目能力描述，已同步根 `README.md`
- [ ] 若新增 ADR，已登记到 `docs/design/adr/README.md` 索引

## 7. 失效文档处理流程

**原则：标记而非删除**（除非涉及合规/隐私问题）。

| 场景 | 处理 |
|---|---|
| 被新文档取代 | 旧文档状态改 `🔄 被取代`，在「取代关系」中指向新文档；正文顶部加一行提示 |
| 结论被推翻但有历史价值 | 状态改 `⛔ 已废止`，保留原文并在顶部说明「该结论已被 ADR-xxx 推翻」 |
| 路径失效 | 立即修正链接；无法修正则标 `⛔ 已废止` |
| 纯重复文件 | **删除副本**，在保留份的元信息块中注明来源 |
| 内容过期但仍大体有效 | 状态改 `📊 分析结论`，在顶部注明「截至 YYYY-MM-DD 的结论，X 项已过时」 |

**禁止**：直接删除仍有引用价值的文档（会导致历史引用与答辩材料出现死链）。
